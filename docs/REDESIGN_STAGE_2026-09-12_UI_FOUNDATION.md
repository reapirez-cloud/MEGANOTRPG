## 1. Контекст этапа

На момент этой записи MEGANOTRPG входит в сильный редизайн интерфейса.

Причина редизайна не в том, что приложение "недостаточно красивое".

Проблема глубже: текущий интерфейс вырос постепенно, по мере появления новых функций, классов, механик, персонажей, зон, предметов и GM-инструментов. В результате разные части приложения получили разные поколения визуальных решений, разные типы навигации и разную логику взаимодействия.

В проекте одновременно существуют несколько визуальных слоёв и поколений UI. Это создаёт ощущение собранного по частям интерфейса и делает приложение похожим на типичный AI-generated dashboard.

Цель текущего редизайна:

- создать узнаваемый визуальный язык MEGANOTRPG;
- перестать наращивать интерфейс добавлением очередных карточек, вкладок и кнопок;
- строить мобильное приложение как цельную систему;
- сделать движение, навигацию, слои, фон и взаимодействия частью дизайна;
- проектировать конечную архитектуру сразу, даже если её реализация займёт много времени;
- не подменять конечную систему временным упрощённым MVP, если заранее известно, что MVP придётся выбросить.

Важный принцип:

**сложную систему можно реализовывать поэтапно, но каждый фундаментальный элемент должен проектироваться как часть конечной архитектуры.**

---

## 2. Что НЕ является целью

Не нужно делать очередной косметический `V6` поверх старого интерфейса.

Не нужно:

- просто менять цвета и border-radius;
- добавлять ещё одну универсальную Card;
- решать каждую новую функцию новой кнопкой;
- делать ещё один слой CSS поверх старых v2/v3/v5/opus;
- использовать готовый UI-kit как визуальную основу приложения;
- выбирать инструменты только потому, что с ними можно быстрее собрать MVP;
- повторять привычный шаблон "иконка + текст + карточка + серый subtitle".

Редизайн должен дать приложению собственное лицо, а не аккуратнее оформить старую структуру.

---

## 3. Глобальная продуктовая структура, известная на этом этапе

На верхнем уровне предполагаются три главных пространства:

- **Чаты**
- **Главная**
- **Рабочее пространство**

Главная является визуальным центром.

В нижней глобальной навигации рассматривается асимметричная композиция примерно 25% / 50% / 25%, где центральная Главная визуально доминирует.

Это направление является частью текущей концепции, но точная геометрия, размеры и анимации ещё не считаются финальной спецификацией.

### Главная

Главная должна стать настоящим Home приложения.

На ней планируются:

- приветствие;
- имя общества / кампании;
- пользовательский аватар;
- атмосферные входы в крупные разделы;
- компактные последние события.

Крупные разделы Главной на этом этапе:

- Что нового;
- Мир;
- Новости общества;
- Достижения;
- Арты;
- Обновления.

### Мир

Мир должен быть самостоятельной предметной областью, а не свалкой разных функций.

Внутри него предполагаются:

- Зоны;
- NPC;
- Лорбук;
- Карта.

Связанные сущности не обязаны находиться на одном экране.

Принцип:

**не объединять разные пользовательские сценарии только потому, что их данные связаны между собой.**

### Рабочее пространство

Рабочее пространство содержит личный и административный контекст.

Для игрока это может включать его персонажей и личные игровые сущности.

Для GM это отдельное рабочее пространство управления персонажами, NPC, зонами, игроками, предметами, материалами и другими административными задачами.

GM-интерфейс не должен быть Player UI с добавленными карандашами и кнопками.

---

## 4. Главный принцип визуального языка

Не строить приложение из одного универсального компонента Card.

Компоненты должны отражать смысл сущности и сценария.

Например, в будущей системе могут существовать разные типы визуальных объектов:

- Section Preview;
- Event Entry;
- Character Presence;
- Workspace Entry;
- Achievement Reveal;
- Story Surface.

Это не обязательные финальные названия компонентов.

Смысл принципа:

**визуальная форма должна следовать роли объекта, а не наоборот.**

Если всё сводится к одной карточке с иконкой, заголовком и подписью, интерфейс снова быстро станет шаблонным.

---

## 5. Фон и атмосфера

Текущий однотонный тёмный фон не считается конечным решением.

В новом UI фундамент должен сразу поддерживать атмосферный фон приложения.

При этом на момент этой записи готового финального фонового изображения может не быть.

Нужно проектировать систему так, чтобы позже можно было подключить фон без переписывания всех экранов.

Система фона должна уметь работать с:

- базовым изображением;
- оттенком / tint;
- затемняющим слоем;
- vignette;
- blur при необходимости;
- слоем, обеспечивающим читаемость foreground content.

Отдельные preview-разделы Главной также должны уметь принимать изображения, которые позже предоставит дизайнер.

Пока изображений нет, интерфейс должен выглядеть завершённым и без них.

---

## 6. Анимации являются частью дизайна

Анимации не должны добавляться в конце как декоративный polish.

Они являются частью поведения интерфейса.

Нужно создать единый motion language для:

- переходов между экранами;
- возврата назад;
- раскрытия персонального контекста;
- переходов shared elements;
- появления и исчезновения поверхностей;
- выбора активного раздела;
- press feedback;
- overlay;
- drag / swipe взаимодействий.

Не нужно разбрасывать случайные `transition: all` по компонентам.

Должны существовать общие типы движения и общие физические профили: быстрые, стандартные, мягкие, плотные, навигационные и т.п.

Точные параметры пока не считаются финальными.

---

## 7. Mobile-first и жесты

Новый интерфейс проектируется как мобильное приложение, а не десктопная панель, уменьшенная до ширины телефона.

Архитектура должна позволять:

- swipe-back;
- drag-to-dismiss;
- long press там, где он естественен;
- pull-to-refresh;
- press states;
- shared-element transitions;
- горизонтальные жесты в тех сценариях, где они действительно полезны.

При этом важные функции нельзя делать доступными только через скрытый жест.

Жесты должны улучшать взаимодействие, а не заменять понятную навигацию.

---

## 8. Personal Reveal

Аватар пользователя не должен быть просто стандартной кнопкой "профиль".

Рассматривается отдельный паттерн Personal Reveal:

- пользователь нажимает на аватар;
- аватар визуально становится origin перехода;
- текущая сцена слегка уходит назад;
- раскрывается быстрый персональный слой;
- из него доступны активный персонаж и личный контекст;
- при дальнейшем переходе интерфейс может естественно продолжиться в полноценный Workspace.

Это должен быть характерный interaction pattern MEGANOTRPG, а не обычный popover из UI-kit.

При этом Personal Reveal не обязан быть единственным способом попасть в Workspace. Глобальный Dock также может давать прямой вход.

---

## 9. Новый App Shell

Старую модель "TopBar + Content + BottomNav" не считать конечной.

Целевое направление предполагает разделение приложения на системные слои:

### Viewport

Корневая область приложения и safe areas.

### Backdrop

Глобальный фон, tint, vignette и другие атмосферные слои.

### Scene

Текущий пользовательский экран.

### Chrome

Глобальные элементы навигации и contextual header.

### Layer

Overlay, dialog, context menu, reveal, notifications и другие transient поверхности.

Названия могут измениться, но разделение ответственности важно сохранить.

Внутренние страницы не должны самостоятельно задавать глобальный фон приложения.

---

## 10. Meganot Dock

Новый нижний Dock должен стать одним из узнаваемых элементов приложения.

На данном этапе обсуждается структура:

- Чаты;
- Главная;
- Пространство.

Главная визуально крупнее боковых областей.

Не делать стандартную панель из трёх одинаковых иконок с подписями.

Нужно отдельно спроектировать:

- геометрию;
- active state;
- selection movement;
- press state;
- поведение на root screens;
- поведение на глубоких nested screens;
- возможность уменьшаться или исчезать там, где нижнюю область занимает другой основной инструмент, например chat composer.

Точное финальное поведение ещё не утверждено.

## 11. Инструменты, выбранные на этом этапе

### Motion for React

Считается базовым инструментом новой UI-системы.

Нужен для:

- shared layout transitions;
- morph между состояниями;
- route transitions;
- drag;
- pan;
- swipe;
- press feedback;
- spring animation;
- AnimatePresence;
- сложных мобильных переходов.

Важно:

Motion выбирается не ради красивого fade. Он должен стать технической основой движения интерфейса.

### Radix Primitives

Считается базовым headless-инструментом для сложных overlay и доступности.

Нужен для:

- Dialog;
- Popover;
- Context Menu;
- focus management;
- keyboard interaction;
- portal;
- dismiss behavior;
- accessibility.

Не использовать Radix Themes как визуальную основу приложения.

Radix должен решать поведение и доступность, а внешний вид должен оставаться Meganot-specific.

### React Router

Считается желательным фундаментом новой навигационной архитектуры.

Текущая ручная hash-routing система может стать слишком хрупкой при появлении большого количества nested routes.

Новый интерфейс потребует нормального navigation stack для сценариев вида:

- Главная → Мир → Зоны → конкретная зона;
- Рабочее пространство → Персонажи → персонаж → Инвентарь → предмет;
- Главная → Достижения → конкретное достижение;
- Чаты → комната.

Важно:

не менять существующую маршрутизацию вслепую.

Нужно отдельно выбрать подход, совместимый с Telegram Mini App, deep links и текущими URL.

### Storybook

Считается важным инструментом процесса дизайна.

Он нужен для того, чтобы проектировать и проверять компоненты независимо от полного приложения.

Например, отдельно должны быть видны состояния:

- Dock;
- Section Preview;
- Personal Reveal;
- Achievement Reveal;
- Workspace Entry;
- Character Presence;
- различные состояния без картинки / с картинкой / с длинным текстом.

Это важно для борьбы с шаблонным AI-интерфейсом.

Компонент сначала должен быть доведён до визуально правильного состояния как часть Meganot UI, и только затем использоваться в конкретном экране.

### Playwright

Считается нужным инструментом QA, но его подключение можно делать после появления нового App Shell.

Нужен для:

- реальных UI-flow тестов;
- проверки навигации;
- проверки overlay и back;
- проверки поведения на мобильном viewport;
- screenshot / visual regression тестов ключевых поверхностей.

Сборка TypeScript не является достаточной проверкой качества интерфейса.

## 12. Что НЕ планируется использовать как визуальную основу

На этом этапе не рекомендуется делать основой нового интерфейса:

- Material UI;
- Ant Design;
- Chakra;
- shadcn как готовый визуальный язык;
- готовые dashboard libraries;
- Lucide как обязательный icon language;
- любую библиотеку, которая навязывает приложению узнаваемый чужой стиль.

Причина:

цель — создать собственный визуальный язык MEGANOTRPG, а не быстро собрать аккуратный generic dashboard.

Отдельные технические идеи или utility-компоненты можно использовать при необходимости, но они не должны задавать внешний вид продукта.

---

## 13. Что пока НЕ нужно добавлять

### Floating UI

Не подключать заранее.

Если позже появится конкретный interaction, для которого Radix недостаточен, решение можно пересмотреть.

### Отдельная gesture library

Пока не требуется, поскольку Motion покрывает основные сценарии жестов и анимации.

### Theme library

Не требуется.

Новая theme/design system должна быть собственной.

### Отдельный пакет для haptics

Не требуется.

Для Telegram Mini App использовать API самой платформы.

### Vaul

Не рассматривать как фундаментальный dependency нового UI на данном этапе.

Если понадобится drawer/sheet с жестами, лучше сделать Meganot-specific компонент на выбранных primitives и motion-инфраструктуре.

## 14. Собственный Meganot UI слой

Приложение не должно напрямую разбрасывать по всему коду вызовы сторонних UI primitives.

Нужно создать собственный слой Meganot UI.

Его назначение:

- скрыть конкретные библиотеки за нашим API;
- сохранить единый visual language;
- централизовать motion;
- централизовать overlay behavior;
- облегчить будущую замену внутренней библиотеки;
- не допустить появления десяти разных реализаций Dialog/Drawer/Surface.

Точные имена и структура каталогов ещё не являются финальными.

Смысл:

**Motion, Radix и Router являются внутренними механизмами. Пользовательские экраны должны работать в терминах Meganot UI.**

---

## 15. Storybook как часть дизайнерского процесса

Новый рабочий процесс должен отличаться от старого.

Не проектировать ключевой компонент только внутри конкретной страницы.

Для важных компонентов сначала необходимо:

1. создать набор состояний;
2. показать компонент отдельно;
3. проверить его с короткими и длинными данными;
4. проверить с изображением и без изображения;
5. проверить active / inactive / disabled / loading / error;
6. проверить движение;
7. при возможности показать дизайнеру;
8. только после этого подключать в полноценный экран.

Это особенно важно для:

- Dock;
- Section Preview;
- Personal Reveal;
- Achievement Reveal;
- крупных workspace patterns.

---

## 16. Telegram Mini App как платформа

Новый интерфейс должен использовать возможности Telegram Mini App там, где они улучшают ощущение мобильного приложения.

В частности, можно использовать haptic feedback для:

- selection change;
- мягкого подтверждения действия;
- success;
- warning;
- error.

Использовать дозированно.

Не превращать каждое нажатие в вибрацию.

Telegram BackButton и системные возможности платформы должны учитываться в новой навигационной архитектуре.

---

## 17. Принцип реализации

Ключевой принцип этого этапа:

**не делать временную упрощённую архитектуру только потому, что её можно реализовать быстрее.**

Допускается:

- реализовывать конечную архитектуру по частям;
- временно встраивать старые модули внутрь нового Shell;
- мигрировать экраны постепенно;
- оставлять старую бизнес-логику, пока новый presentation layer её использует.

Не допускается:

- создавать заведомо временный новый BottomNav;
- делать очередную временную систему Card;
- откладывать фундаментальные возможности UI "на потом", если уже известно, что они нужны;
- принимать архитектурное решение только ради скорости первой реализации.

---

## 18. Что сохраняется из старой системы

Редизайн UI не означает автоматическую перепись механического ядра.

На этом этапе предполагается максимально сохранять:

- Character Engine;
- Character Runtime;
- Inventory Engine;
- классы и подклассы;
- spell system;
- permissions;
- Supabase data и существующие owners;
- работающие бизнес-процессы.

Старые страницы могут временно жить внутри нового Shell до появления полноценной замены.

Новый UI должен постепенно заменить presentation layer без бессмысленного одновременного переписывания всей системы.

- проверять текущий код перед каждой реализацией;
- сохранять идею собственного Meganot UI layer.

Если дата значительно позже:

- НЕ считать, что редизайн всё ещё идёт;
- НЕ устанавливать библиотеки только потому, что они перечислены здесь;
- НЕ переделывать уже завершённый интерфейс по этому документу;
- сначала найти более новые design docs, ADR, changelog и актуальный код;
- рассматривать этот файл как историческую запись решений этапа 12.09.2026.
