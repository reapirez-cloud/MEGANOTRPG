# Character UX Redesign — первичный аудит и направление

> Status: **ACTIVE REDESIGN / PRIMARY AUDIT / NOT FINAL SPEC**
>
> Branch context: `dev`
>
> Этот документ является обязательной отправной точкой перед работой над интерфейсом персонажа, GM character management, созданием/редактированием PC/NPC, классами/подклассами, расой, инвентарём и предметами.
>
> **ВАЖНО:** это не истина в последней инстанции и не замороженная спецификация. Это первичный аудит текущей системы после того, как приложение накопило достаточно реальных классов, механик и GM-сценариев, чтобы стало видно, какие UX-решения не масштабируются. Решения ниже можно и нужно уточнять в ходе редизайна, если новые данные или реальные сценарии покажут лучший путь.

---

## 1. Почему начат полный редизайн

Текущий интерфейс персонажа собирался постепенно, по мере появления функций. На раннем этапе было неясно, какие реальные сценарии будут нужны игроку и GM после подключения большого числа классов, подклассов, ресурсов, заклинаний, предметов, скрытых механик и NPC.

Из-за этого интерфейс рос локальными решениями:

- новые функции добавлялись рядом с существующими;
- большие редакторы открывались в bottom sheet;
- один и тот же экран пытался быть одновременно листом игрока и панелью GM;
- классы, расы, ресурсы и механики CE постепенно получили собственные вложенные интерфейсы;
- навигация росла вкладками, подвкладками, long press, `•••`, карандашами и скрытыми действиями;
- новые визуальные поколения накладывались поверх старой информационной архитектуры.

Итог: функциональность стала заметно сильнее, чем UX вокруг неё.

**Редизайн начат не ради нового внешнего вида. Он нужен ради нового способа взаимодействия с системой.**

---

## 2. Главный принцип редизайна

### Удобство важнее количества видимых функций

Нельзя решать рост возможностей приложения правилом:

> «Появилась новая функция → добавим ещё одну кнопку, вкладку или карточку».

Цель редизайна прямо противоположная:

- уменьшать количество решений, которые пользователь должен принимать одновременно;
- показывать действие там, где оно естественно требуется;
- разделять просмотр, игру и администрирование;
- убирать технические понятия движка из основного UX;
- уменьшать вложенность;
- использовать progressive disclosure: сложные возможности появляются только тогда, когда реально нужны;
- один сценарий должен иметь один очевидный путь.

**Больше функций не должно автоматически означать больше постоянных кнопок на экране.**

Если новая функция требует ещё одной постоянно видимой кнопки, сначала надо проверить, не является ли это признаком неправильной структуры.

---

## 3. Что сейчас считается системной проблемой

### 3.1 Player View и GM Management смешаны

Сейчас один и тот же character surface пытается обслуживать:

1. игрока, который играет своим персонажем;
2. GM, который настраивает персонажа;
3. техническое управление Character Engine.

Это разные задачи и разные когнитивные режимы.

Игроку нужен быстрый доступ к состоянию персонажа и игровым возможностям.

GM нужен контроль над сущностью персонажа, сборкой, доступом, инвентарём, механиками и скрытой информацией.

Character Engine diagnostics нужны редко и не должны доминировать ни в одном из этих интерфейсов.

### 3.2 `CharacterGameFrame` стал UI-панелью вместо технической оболочки

`CharacterGameFrame` содержит административный интерфейс поверх дочернего character UI:

- состояние жизни;
- отдых;
- ресурсы;
- class/subclass bindings;
- race/subrace assignments;
- CE source suppression;
- template assignment editor.

Это создаёт второй центр управления персонажем поверх основного интерфейса.

Целевое направление: `CharacterGameFrame` должен стремиться обратно к роли runtime/provider boundary, а не административного экрана.

### 3.3 `CharacterProfileV2` владеет слишком большим количеством UX-обязанностей

Сейчас в одном surface находятся:

- лист;
- класс;
- заклинания;
- инвентарь;
- дневник;
- арты;
- аватар;
- редакторы;
- reference;
- runtime states;
- комментарии;
- вложенная навигация.

Такой компонент трудно менять без побочных эффектов и почти невозможно последовательно редизайнить.

### 3.4 Большие редакторы используются как bottom sheet

Bottom sheet подходит для:

- короткого выбора;
- небольшого contextual action menu;
- подтверждения;
- быстрых одношаговых операций.

Он плохо подходит для:

- создания персонажа в 7 шагов;
- сложного редактирования предмета;
- управления сборкой персонажа;
- больших форм;
- полноценных административных поверхностей.

**Во время редизайна большие editor flows должны становиться полноценными экранами/routes.**

### 3.5 Редактирование и создание смешаны

`CharacterCreationWizard` используется и для создания, и для редактирования существующего персонажа.

Это приводит к ситуации, когда изменение одного аспекта персонажа требует проходить структуру мастера создания.

Целевое направление:

- создание остаётся guided flow;
- редактирование существующего персонажа становится section-based;
- NPC получает быстрый путь создания;
- расширенный лист NPC заполняется позже при необходимости.

### 3.6 Class / subclass UX раскрывает внутренности системы

Сейчас GM сталкивается с понятиями CE/template binding/source suppression почти напрямую.

Для обычной работы GM должен видеть доменную модель:

- Класс;
- Уровень класса;
- Подкласс;
- Раса;
- Подраса;
- Мультикласс.

Внутренние CE sources, contribution groups, suppression и diagnostics должны жить в расширенном/диагностическом режиме.

---

## 4. Известные симптомы, подтвердившие необходимость редизайна

На момент первичного аудита уже наблюдаются:

- некоторые character runtime сборки падают целиком при ошибке одного источника механики;
- UI класса визуально воспринимается как незавершённая служебная панель;
- карандаш класса/подкласса меняет состояние редактора ниже по той же шторке и выглядит как неработающая кнопка;
- обычное назначение нового класса может быть интерпретировано системой как добавление мультикласса;
- общий уровень персонажа синхронизируется как сумма class assignments, поэтому ошибочное добавление второго класса может создать персонажа выше ожидаемого уровня;
- смена класса и намеренное добавление мультикласса не разведены как отдельные UX-операции;
- большой объём runtime/internal controls отображается слишком близко к основному пользовательскому интерфейсу;
- inventory navigation имеет избыточную глубину для обычного использования;
- reusable item definition и конкретный item instance пока частично смешаны в редакторе;
- GM workspace и character sheet конкурируют за роль главного места управления персонажем.

Эти проблемы нельзя считать набором независимых мелких багов. Они являются сигналами одной архитектурной UX-проблемы.

## 5. Целевая ментальная модель

### 5.1 Игрок

Игрок открывает персонажа, чтобы **играть персонажем**, а не администрировать его модель.

Первый экран должен отвечать на вопросы:

- кто я;
- в каком я состоянии;
- что мне доступно сейчас;
- куда перейти за нужным игровым действием.

Приоритеты:

- HP / temp HP;
- AC;
- initiative / speed;
- conditions;
- важные class resources;
- быстрые игровые действия;
- ясные входы в способности, магию, вещи и остальное.

Не нужно превращать первый экран в каталог всех доступных функций.

### 5.2 GM

GM открывает персонажа, чтобы **управлять сущностью персонажа**.

Это отдельный административный контекст.

Целевые разделы могут включать:

- Overview;
- Build;
- Combat/base sheet;
- Inventory;
- Magic;
- Features/effects;
- Access/visibility;
- NPC-specific settings;
- Diagnostics.

Точный набор и названия НЕ являются финальной спецификацией. Важно разделение обязанностей.

### 5.3 Preview

GM должен иметь возможность явно открыть:

**«Вид игрока»**

Это должно быть отдельное состояние просмотра, а не попытка мысленно игнорировать GM-only элементы.

Особенно важно из-за:

- hidden curse information;
- private effects;
- NPC discovery visibility;
- GM-only notes;
- assigned-player permissions.

## 6. Навигационный принцип

Не строить новые интерфейсы как бесконечное размножение вкладок.

Предпочтительная модель:

```text
глобальный раздел
→ персонаж
→ раздел персонажа
→ конкретный объект / editor
```

Например:

```text
Я
→ Ниель
→ Инвентарь
→ Шёпот
```

Для GM:

```text
Панель
→ Персонажи
→ Ниель
→ Сборка
→ Воин
```

На каждом уровне должен быть понятный back/navigation context.

**Не создавать вкладку внутри вкладки только потому, что это технически проще.**

---

## 7. Full-screen editor vs sheet

### Использовать sheet/dialog для:

- подтверждений;
- contextual actions;
- короткого выбора;
- назначения игрока;
- небольших одношаговых настроек.

### Использовать полноценный экран для:

- Build Editor;
- создания PC;
- расширенного создания NPC;
- редактирования основных данных персонажа;
- сложного item editor;
- сложного spell/feature editor;
- любых многошаговых или длинных форм.

Правило:

> Если пользователь должен читать, прокручивать, сравнивать несколько секций или принимать несколько связанных решений, это почти наверняка не bottom sheet.

---

## 8. Character Build должен стать отдельным продуктовым понятием

Класс, подкласс, уровень класса, раса и мультикласс должны восприниматься как **сборка персонажа**, а не как template bindings.

Пример пользовательской модели:

```text
Воин · 5 уровень
└ Чемпион
```

Основные операции:

- изменить уровень;
- сменить подкласс;
- сменить класс;
- добавить мультикласс отдельно и осознанно;
- удалить дополнительный класс;
- изменить расу/подрасу.

### ВАЖНО

**«Сменить класс» и «Добавить мультикласс» не должны быть одной операцией.**

Обычная смена класса должна восприниматься системой как замена, а не как неявное создание дополнительного class assignment.

Точный backend-контракт будет спроектирован отдельно.

---

## 9. NPC

NPC не всегда нужен полный D&D character sheet.

Редизайн должен поддерживать минимум два сценария:

### Быстрый NPC

Минимально:

- имя;
- роль;
- портрет;
- описание;
- видимость;
- зона / habitat при необходимости.

Создаётся быстро.

### Полный NPC

При необходимости расширяется:

- abilities;
- combat;
- mechanics;
- inventory;
- spells;
- features;
- resources.

Не заставлять GM заполнять полный character wizard ради торговца, свидетеля или стражника.

---

## 10. Inventory / Items

Нужно логически разделить:

### Item Definition

Что предмет представляет собой вообще:

- название;
- описание;
- арт;
- категория;
- equipment slot;
- базовая механика;
- curse definition;
- default behavior.

### Character Item Instance

Что происходит с конкретным экземпляром:

- quantity;
- equipped state;
- charges;
- discovered/revealed state;
- индивидуальные изменения;
- instance-specific runtime state.

Инвентарь игрока должен быть оптимизирован под **поиск и использование**, а не под структуру хранения данных.

Избегать лишней иерархии вида:

```text
Вещи → Экипировка → Слот → Предмет
```

если тот же сценарий можно решить одним экраном, фильтром и понятными карточками.

## 11. Design system cleanup

Сейчас одновременно существуют несколько поколений UI/CSS:

- `character-profile-v3.css`;
- `character-profile-v5.css`;
- `character-profile-opus.css`;
- `ui-v2.css`;
- старые character sheet/system layers;
- специализированные локальные стили.

Новый редизайн не должен становиться ещё одним `v6` поверх них.

Нужен единый набор presentation primitives, например:

- Page;
- PageHeader;
- Section;
- ListRow;
- Stat;
- ActionMenu;
- Dialog;
- FullScreenEditor;
- EmptyState;
- ErrorState.

Конкретные имена не являются обязательными. Обязательна идея: **одно новое UI-основание вместо очередного параллельного поколения.**

Старые стили удаляются постепенно по мере миграции экранов.

---

## 12. Что НЕ надо делать во время редизайна

Не делать:

- косметический `V6` без изменения структуры;
- ещё один глобальный character tab только потому, что появилась функция;
- ещё одну кнопку на главном экране для каждой возможности;
- длинные формы в маленьких overlay;
- скрывать основные действия только за long press;
- делать GM UI как Player UI + набор карандашей;
- показывать внутреннюю терминологию CE как основной пользовательский язык;
- переписывать Character Engine только ради нового UI, если его контракт можно сохранить;
- удалять рабочую механику до появления нового эквивалентного пути.

---

## 13. Что желательно сохранить

Редизайн не означает полный rewrite приложения.

Желательно сохранить и переиспользовать, где это разумно:

- Character Runtime / resolved contract;
- Character Engine;
- Inventory Engine;
- template/class/subclass mechanics;
- permissions;
- source suppression как диагностический инструмент;
- hidden curse semantics;
- item library architecture;
- spell catalog/runtime;
- существующие backend owners.

Основной объект переделки: **presentation layer + application interaction model вокруг существующих движков.**

---

## 14. Ошибки runtime и UX

Character Engine может оставаться строгим к механическим ошибкам, но пользовательский интерфейс не должен становиться полностью бесполезным из-за одной неисправной механики.

Направление для последующей архитектуры:

- preflight классов и подклассов до публикации;
- diagnostics с указанием виновного source/mechanic;
- last-known-good / degraded presentation там, где это безопасно;
- возможность открыть базовую информацию персонажа даже при частичной runtime-проблеме;
- GM diagnostic actions отдельно от Player View.

Это направление требует отдельного технического проектирования. Не реализовывать ad hoc fallback без проверки механической корректности.

## 15. Предварительный порядок работ

Это ориентир, а не жёсткий roadmap.

### Phase 0 — Freeze cosmetic redesigns

Не создавать новые визуальные поколения поверх старой структуры.

### Phase 1 — New Character Shell / navigation

Определить новые маршруты и page hierarchy.

Можно временно помещать существующие рабочие модули внутрь нового shell, чтобы не переписывать всё одновременно.

### Phase 2 — Player Character Home

Сделать игровой home персонажа:

- status;
- ключевые ресурсы;
- быстрые действия;
- понятные входы в разделы.

### Phase 3 — GM Character Admin

Отделить административный интерфейс от Player View.

### Phase 4 — Character Build

Нормализовать class/subclass/race/multiclass UX и операции.

### Phase 5 — Creation and editing

Разделить:

- PC creation;
- quick NPC;
- full NPC;
- existing character section editors.

### Phase 6 — Inventory / item workflow

Нормализовать definition vs instance и уменьшить навигационную глубину.

### Phase 7 — UI cleanup

Удалять старые presentation layers после миграции каждого surface.

---

## 16. Как ИИ должен использовать этот документ

Перед работой над redesign-related задачей:

1. Прочитать этот файл.
2. Проверить актуальное состояние кода, потому что аудит может устареть.
3. Не считать предложенную структуру финальной истиной.
4. Сохранять главный product intent:
   **меньше когнитивной нагрузки, меньше вложенности, меньше постоянно видимых controls, ясное разделение Player / GM / Diagnostics.**
5. Не добавлять новый UI-слой поверх старого без серьёзной причины.
6. При наличии более простого UX предлагать его, даже если он отличается от примеров в этом файле.
7. Не путать «больше возможностей» с «больше кнопок».
8. При изменении фундаментального направления обновлять этот аудит или создавать следующий design decision document, чтобы будущая работа не основывалась на устаревшей картине.

## 17. Статус решений

### Считается установленным направлением

- требуется сильный редизайн, а не косметический polish;
- текущая character UI architecture считается переходной;
- Player View и GM Management должны быть существенно разделены;
- сложные редакторы не должны жить в маленьких overlay;
- рост функций не должен приводить к линейному росту кнопок и вкладок;
- technical CE controls должны быть вторичными;
- новый дизайн должен уменьшать трение, а не просто красиво организовывать текущую сложность.

### Пока НЕ считается финальным решением

- точный набор экранов;
- названия разделов;
- количество navigation levels;
- расположение каждого action;
- окончательная визуальная стилистика;
- окончательный route schema;
- точный компонентный API нового UI;
- точный backend contract для replace class / multiclass;
- конкретная degraded-runtime стратегия.

---

## 18. Критерий успеха

Редизайн считается успешным не тогда, когда интерфейс выглядит новым.

Он успешен, если:

- игрок без объяснений понимает, где состояние его персонажа и как им играть;
- GM быстро находит нужного персонажа и меняет нужную часть без путешествия по мастерам и overlay;
- частые действия требуют мало шагов;
- редкие и сложные возможности доступны, но не засоряют основной интерфейс;
- новые классы, ресурсы и механики не требуют каждый раз придумывать новый постоянный UI-контрол;
- интерфейс масштабируется по сложности системы без превращения в панель разработчика.
